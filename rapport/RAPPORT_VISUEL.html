Contexte

Le problème et la réponse apportée

Un coach de vie gère aujourd'hui ses rendez-vous par téléphone et messagerie : doubles réservations, oublis, aucune visibilité sur son activité. L'application permet au client de réserver seul un créneau, et au coach de piloter son planning depuis un espace d'administration.

Lecture seule

Visiteur

Consulte les prestations, les créneaux déjà occupés et les témoignages. Peut s'inscrire ou se connecter. Toute action d'écriture le renvoie vers le formulaire de connexion.

GET /services · GET /rendezvous/disponibilites · GET /avis

Connecté · JWT

Client

Réserve un créneau, consulte son historique, annule une demande encore en attente, et dépose un avis après une séance terminée.

POST /rendezvous · GET /mes-rendez-vous · PUT /:id · POST /avis

RBAC · adminOnly

Administrateur / coach

Tableau de bord (compteurs, chiffre d'affaires), validation et changement de statut des demandes, CRUD des prestations, liste des comptes.

GET /rendezvous · GET /stats · POST-PUT-DELETE /services

Règles de gestion
  1. Un créneau date + heure ne peut être réservé que par un seul rendez-vous actif.
  2. Un rendez-vous doit être dans le futur et porter sur une prestation active.
  3. Un client ne peut annuler que sa propre demande, et seulement si elle est en_attente.
  4. Un avis n'est possible qu'après une séance termine, une seule fois, par le client concerné.
  5. Une prestation liée à au moins un rendez-vous ne peut pas être supprimée.

Le panneau d'administration n'est pas une seconde application : c'est une vue de la même SPA, affichée uniquement si user.role === 'admin'. Le serveur revérifie ce rôle à chaque requête — l'interface n'est jamais la seule barrière de sécurité.

Bannière, catalogue des prestations, témoignages. À gauche : AuthCard si visiteur, BookingForm si client connecté.

Historique complet, annulation d'une demande en attente, dépôt d'un avis sur une séance terminée.

Pas de React Router : une seule variable d'état view suffit, ce qui évite une dépendance et la réécriture d'URL côté hébergeur. La sécurité, elle, reste sur le serveur.

Architecture

Trois couches, une seule chaîne de responsabilités

Le front-end ne parle jamais à la base : il appelle une API REST, qui seule connaît MongoDB. Chaque couche a un rôle unique — c'est la séparation des responsabilités (SoC).

Pourquoi cette séparation ?

Changer de base ou d'interface ne casse pas l'autre côté. Les règles métier sont testables et réutilisables : la même fonction createRendezVous sert au site, et servirait demain à une application mobile.

Le trajet d'une requête

POST /api/rendezvous → cors → express.json() → routeur → protect → contrôleur → modèle Mongoose → Atlas → réponse JSON.

Qui fait quoi, et qui ne fait surtout pas quoi

CoucheResponsabilitéInterdit
Modèle (Mongoose)Structure, types, validation, index, relationsManipuler req ou res
ContrôleurRègles métier, accès aux modèles, code HTTPDéclarer une URL
RouteAssocier une URL à des middlewares puis à un contrôleurContenir de la logique métier
MiddlewareSécurité transversale : JWT, rôle, erreursAccéder directement aux collections
Composant (React)Affichage, état local, envoi de requêtesParler à MongoDB

Base de données04 / 08
Modèle de données

Quatre collections, quatre relations

Le rendez-vous est l'entité centrale : il relie un client à une prestation, et donne lieu à un avis. Les flèches rouges matérialisent les références Mongoose (ref) exploitées par .populate().

relation 1:N matérialisée par une référence relation secondaire (client → avis) entité centrale

La jointure en pratique

// server/src/controllers/rendezVousController.js
const rdv = await RendezVous.find({ client: req.user._id })
  .populate('service', 'nom duree prix')
  .populate('avis')
  .sort({ date: -1, heure: -1 });

1 requête au lieu de 1 + N : Mongoose regroupe les identifiants et interroge services puis avis en une seule passe.

Pourquoi date est une chaîne ?

Un objet Date stocké en UTC puis réaffiché en heure locale décale souvent le jour d'un cran (2026-11-15 devient le 14). En stockant « AAAA-MM-JJ » et « HH:MM », le tri lexicographique reste exact, la comparaison aussi, et aucun fuseau horaire n'intervient.

Les quatre relations, telles qu'elles sont déclarées

RelationCardinalitéChamp de référenceLecture côté serveur
User → RendezVous1 — NRendezVous.client.populate('client', 'name email phone')
Service → RendezVous1 — NRendezVous.service.populate('service', 'nom duree prix')
RendezVous → Avis1 — 1Avis.rendezVous (unique).populate('avis') via champ virtuel

Sécurité05 / 08
Authentification

Le trajet d'un token, de la connexion à la requête protégée

Le mot de passe ne quitte jamais la base sous forme lisible : il est comparé via bcrypt.compare. Le serveur renvoie ensuite un JWT signé, que le navigateur renvoie à chaque appel. Aucune session n'est stockée côté serveur.

Trois barrières, pas une

MenaceContre-mesure
Mot de passe volé en baseHachage bcrypt + sel (facteur 10)
Réserver au nom d'autruiclient = req.user._id, jamais le body
Lire les RDV d'un autreContrôle propriétaire → 403
Se faire passer pour adminrole forcé à client ; adminOnly
Session éternelleexpiresIn: '1d' + TokenExpiredError

L'intercepteur Axios

// client/src/api/axiosClient.js
axiosClient.interceptors.request.use((config) => {
  const token = localStorage.getItem('token');
  if (token) config.headers.Authorization =
    `Bearer ${token}`;
  return config;
});

Aucun composant ne manipule le token : il est posé une seule fois, automatiquement, sur toutes les requêtes.

Anatomie du token : trois parties, une seule signature

header

{ "alg": "HS256", "typ": "JWT" }

Algorithme de signature et type de jeton.

payload

{ "id": "…", "role": "client", "exp": … }

Lisible par tous : on n'y met jamais de mot de passe.

signature

HMACSHA256(header + payload, JWT_SECRET)

Une modification du payload invalide la signature → 401.

Parcours06 / 08
Fonctionnement

De la réservation à l'avis : un cycle maîtrisé

Ce que fait le client, et ce que fait le serveur

1

Choisir une prestation

La carte « Réserver » écrit l'identifiant dans Redux (ui.selectedServiceId) et fait défiler vers le formulaire.

2

Choisir une date

Le champ est borné à aujourd'hui (min={todayISO()}) : une date passée est impossible à saisir.

3

Demander les créneaux

GET /rendezvous/disponibilites?date=…

Le serveur ne renvoie que les heures occupées : aucune donnée personnelle ne fuit.

4

Choisir un créneau

Les heures prises ou déjà passées sont désactivées et barrées.

5

Envoyer la demande

POST /rendezvous

Le serveur revérifie : créneau futur, prestation active, aucun conflit.

6

Suivre et clôturer

Le coach confirme puis termine. Le client peut alors déposer un avis, une seule fois.

La règle qui évite les doubles réservations

// vérifié côté serveur, pas seulement dans l'interface
const conflit = await RendezVous.findOne({
  date,
  heure,
  statut: { $in: ['en_attente', 'confirme'] }
});

if (conflit) {
  return res.status(409).json({
    message: 'Ce creneau est deja reserve'
  });
}

Pourquoi revérifier côté serveur ?

Désactiver un bouton dans le navigateur ne protège de rien : n'importe qui peut appeler l'API directement. Deux clients qui cliquent à la même seconde passent tous les deux la validation de l'interface — seul le contrôle serveur, appuyé par l'index { date, heure }, tranche.

Et l'annulation ?

Un client ne peut envoyer que { statut: 'annule' }. Toute autre valeur renvoie 403 : il ne peut ni confirmer, ni terminer son propre rendez-vous.
